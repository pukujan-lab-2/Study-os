## Cloud/repo P0 review — changes needed before merge

The implementation covers the advertised P0 surface and CI is green, but contract/failure-mode review found several integrity gaps that should be closed before P0 acceptance:

1. **Subject-scoped evidence provenance.** `StudyOSService._resolve_evidence` currently validates existence only. A derived event, assessment, representation outcome, checkpoint, or FOSSIL export for subject A can therefore cite an otherwise-valid evidence ID belonging to subject B. Evidence used to derive learner state must be scoped to the requested subject (and session where the operation is session-bound). Add rejection tests for cross-subject evidence references.

2. **Representation outcome requires behavioral assessment evidence.** `docs/VALIDATION_STRATEGY.md` and `docs/LUNA_LOCAL_HANDOFF.md` require outcomes to reference a real intervention plus behavioral evidence/assessment. `record_representation_outcome` verifies the intervention but currently accepts any resolvable evidence type. Require at least one assessment belonging to the same subject; preserve the existing synthetic supported + faded assessment path.

3. **`doctor` must validate checkpoint source sessions as well as evidence IDs.** `docs/DATABASE_CONTRACT.md` requires checkpoint evidence/source IDs to be resolvable. Current `doctor` checks checkpoint `evidence_ids_json` but not `source_session_ids_json`. Add corruption/failure-injection coverage for a stale/missing source session reference.

4. **Restore swap needs rollback safety.** `restore()` stages files, moves the current DB/evidence aside, then installs the backup. An exception between those filesystem moves can leave the active runtime partially replaced with no rollback to the previous DB/evidence pair. Add failure injection around the swap and restore the previous pair on failure before treating backup/restore as failure-safe.

5. **FOSSIL export file + idempotency commit should not leave orphan durable artifacts on transaction failure.** `export_fossil()` writes the JSON file before the DB/idempotency transaction commits. Clean up the staged export on failure (or stage + atomically publish after commit with a recoverable protocol) and test the interrupted-write path.

I also changed the PR body from `Fixes #5` to `Refs #5`: Issue #5 contains P1/P2 acceptance work, so merging this P0 PR must not auto-close the parent tracker.

Existing CI for `a280eb4` is green; these are review gaps not detected by the current 28-test suite.

One additional P0 acceptance gap from the checkpoint path: `docs/VALIDATION_STRATEGY.md` explicitly says checkpoint creation must never mark an untested capability as passed. `checkpoint()` currently accepts arbitrary `capability_state` after only resolving the supplied evidence IDs; it does not verify that a `pass*` capability claim is supported by a same-subject assessment (and `pass_unaided` by an unaided assessment). Several current tests checkpoint `state_prediction: pass_unaided` using only artifact/event evidence, so the test suite is currently encoding the gap rather than catching it.

Please treat this as blocker #6: add capability-state provenance validation plus a rejection test for unsupported `pass*` claims, and update checkpoint fixtures so passed capabilities cite their supporting assessment IDs.
