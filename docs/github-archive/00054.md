## Purpose

Define the focused P3.0 product and system contracts for the current highest-priority runtime problem: real GPT learning sessions are producing valuable operational learner evidence while the GPT -> local Study OS path can return 502/unknown results.

## Adds

- `docs/P3_DURABLE_EVIDENCE_CAPTURE_PDD.md`
  - defines the product guarantee as **no silent learner-evidence loss**;
  - distinguishes durably captured from known uncertain/missing evidence;
  - makes raw/source evidence -> normalized operations -> derived learner/system state an explicit durable hierarchy;
  - defines retry, restart, reconciliation, privacy, minimal learner-burden and success requirements.

- `docs/P3_DURABLE_EVIDENCE_CAPTURE_SDD.md`
  - defines the logical durability boundary;
  - separates source-turn capture from semantic processing and derived state;
  - defines idempotency/fingerprint behavior;
  - defines commit-before-ack and unknown-result semantics;
  - defines pre-receipt transcript reconciliation/backfill without rewriting history;
  - defines `doctor`, provenance, ordering, backup/restore and focused failure-injection acceptance tests;
  - explicitly defers frontend, Postgres, broad SWE cleanup, adaptive promotion and wholesale runtime refactors.

## Architectural position

The accepted local-first architecture remains unchanged:

`GPT -> secure/private Study OS transport -> local Study OS runtime -> SQLite + private evidence store`

FOSSIL remains optional/downstream. GitHub remains source/spec/research/curated-data infrastructure rather than the live learner database.

Implementation code remains replaceable. Persistent evidence identities, provenance, idempotency semantics, migrations and reconciliation behavior are the durable assets.

## Boundary

Planning/specification only. No runtime code, SQLite migration, MCP contract, local deployment configuration, learner data, frontend or adaptive authority changes are included.

## Next implementation action after acceptance

Before modifying the runtime, reproduce/localize the current 502 boundary using sanitized diagnostics and determine whether failure occurs before local receipt, during handling/persistence, or after commit while returning the result. Then implement only the smallest changes required by the P3.0 invariants.
