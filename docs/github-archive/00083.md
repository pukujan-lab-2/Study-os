## Why this matters

Before the web-app track writes code, it needs researched, testable specs. Otherwise the web surface will drift from the deterministic-controller architecture and the privacy rules.

## Outcome

A spec PR under `docs/webapp/` containing:
- research summary with sources;
- architecture;
- property-driven specs (invariants per component);
- success and fail conditions for sessions and for the product;
- data model;
- learner memory schema and scope rules;
- auth, hosting, and analytics recommendations (including a plain answer on Power BI);
- LLM route choice with a price snapshot and live probe results;
- agent-vs-agent test design;
- a phased build plan with a thin first slice.

## Scope

- In scope: docs only (`docs/webapp/**`), a proposed decision D016, a task file, and a short HANDOFF note.
- Out of scope: app code, deployments, infrastructure changes, branch `task/SOS-0002-*`, and any private-repository content.

## Acceptance criteria

- [ ] `docs/webapp/` covers every item listed under Outcome, with sources.
- [ ] Every component spec lists invariants that tests can check.
- [ ] Every child issue of the epic is linked from the build plan.
- [ ] Repository validation, unit tests, and PCM preflight stay green. Required CI passes and auto-merge is enabled.
- [ ] No private-repository content is included.
