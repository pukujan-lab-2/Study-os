# Issue #4: [Accepted Architecture] Local-first Study OS runtime and @StudyOS orchestration

- State: closed (2026-09-03)
- Opened by Pukujan on 2026-08-24
- Original: https://github.com/Pukujan-lab/Study-os/issues/4

## Decision

Study OS v0.1 will be **local-first**. The live learner state, checkpoints, assessments, representation outcomes, and private evidence live in a local Study OS runtime (initially WSL). GitHub remains the versioned source for code, schemas, research, issue logs, plugin/app definitions, tests, and curated/redacted artifacts.

Stable architecture reference: [`docs/LOCAL_RUNTIME_ARCHITECTURE.md`](../blob/main/docs/LOCAL_RUNTIME_ARCHITECTURE.md)

## Why this change

The initial GitHub-centered bootstrap was useful for research/reproducibility, but GitHub should not behave like an operational database. A learning session can create many high-frequency events, attempts, representation switches, scores, checkpoints, and private transcript artifacts. Those need low-latency structured storage and strong privacy boundaries.

## Runtime ownership

### Local Study OS service owns

- subjects/projects/domains/concepts;
- sessions and normalized messages;
- learning events/episodes;
- attempts and assessments;
- representation interventions/outcomes;
- assistance/fading state;
- learner-state derivations;
- checkpoints/current pointer;
- retention/transfer probes;
- private raw transcript/evidence metadata and local artifacts.

### GitHub owns

- Study OS source code;
- custom app/MCP definitions and semantic tool contracts;
- DB schemas/migrations;
- Lesson IR and deterministic representation specs;
- tests/fixtures;
- research, decisions, requirements, agent handoff;
- curated/redacted dataset releases;
- optional FOSSIL export/mapping code.

**Runtime invariant:** recording an answer, checkpointing, resuming, or scoring must not require a GitHub commit or GitHub Actions run.

## Initial WSL stack

```text
WSL
├── Study OS service
│   ├── MCP semantic tool server
│   └── optional local admin HTTP/FastAPI API
├── SQLite
│   └── operational learning state
├── ~/.study-os/evidence/
│   └── immutable private transcripts/media + hashes
└── Study-os git clone
    ├── schemas/migrations
    ├── lesson definitions
    └── tests
```

SQLite is sufficient for Subject 001/single-user R0. Keep the data/service contracts migration-friendly so Postgres can replace SQLite later without changing `@StudyOS` semantic operations.

## Project-agnostic DB requirement

The local DB should be reusable by future learning domains and sessions. Do not hard-code only DSA-specific tables.

Minimum model:

- `subjects`
- `projects`
- `domains`
- `concepts`
- `sessions`
- `messages` / `raw_artifacts`
- `learning_events`
- `episodes`
- `attempts`
- `assessments`
- `representations`
- `interventions`
- `representation_outcomes`
- `checkpoints`
- `retention_probes`

Domain-specific details may use versioned payloads/extensions, but provenance/session/checkpoint semantics should stay reusable.

## One `@StudyOS` orchestration surface

The user should only need one app/plugin surface.

Desired commands:

```text
@​StudyOS start
@​StudyOS resume
@​StudyOS checkpoint
@​StudyOS status
@​StudyOS retention
@​StudyOS export-fossil
```

ChatGPT internally calls semantic tools such as:

- `start_session`
- `resume`
- `get_current_state`
- `record_learning_event`
- `record_attempt`
- `record_assessment`
- `record_representation_intervention`
- `record_representation_outcome`
- `checkpoint`
- `schedule_retention_probe`
- `get_next_probe`
- `status`
- `export_fossil`

Do **not** expose arbitrary `run_sql`, shell execution, or unrestricted file/database mutation to the conversational model.

## How ChatGPT reaches a WSL-local service

ChatGPT cannot directly connect to a server that exists only at `localhost` on the learner's machine.

Target path:

```text
ChatGPT
  -> @​StudyOS custom app
  -> MCP connection
  -> secure/private MCP tunnel
  -> WSL Study OS MCP server
  -> SQLite + private evidence store
```

Current OpenAI guidance says local/private MCP servers are not connected directly; use Secure MCP Tunnel (or another deliberately secured remote HTTPS path) for a private network/developer machine. The exact custom-app/write capability is plan/workspace dependent and must be verified when integrating.

**Security requirement:** never expose an unauthenticated WSL port publicly just to make ChatGPT reach it.

## GitHub Actions decision

GitHub Actions is **not part of the runtime**.

It may remain as optional repository CI for:

- schema/migration checks;
- unit/integration tests;
- plugin/app contract tests;
- privacy/public-data checks.

The local runtime must run its own startup/write-time validation regardless of whether Actions exists or last passed.

If GitHub Actions becomes distracting during R0, it can be reduced/disabled without changing the live Study OS architecture.

## Put integrity enforcement in Study OS itself

The local service should enforce before writes/startup:

- migration/schema compatibility;
- checkpoint pointer integrity;
- evidence provenance requirements;
- immutable raw artifact hashes;
- no derived learner-state claim without evidence links;
- valid representation/lesson versions;
- semantic event/checkpoint schemas.

Provide a local `doctor` / `health` operation.

## Checkpoint source of truth

Once the local runtime exists:

```text
local DB checkpoint = canonical live learner state
GitHub checkpoint snapshot = optional curated/reproducibility export
```

The existing GitHub `CURRENT.json` is bootstrap/research state, not the desired long-term operational datastore.

## Manual vs automated checkpointing

### R0/manual

Use explicit:

- `@StudyOS checkpoint`
- `@StudyOS resume`

### Later/automatic

When Study OS receives session events directly, checkpoint at meaningful deterministic boundaries:

- session close;
- confirmed breakthrough + behavioral retest;
- material assistance/fading change;
- lesson boundary;
- transfer/retention assessment;
- persistent failure that changes next-session plan.

Do not assume ordinary ChatGPT can silently detect conversation end and persist data without app/tool calls.

## FOSSIL boundary

FOSSIL remains downstream/optional.

Promote only durable knowledge such as:

- Golden Learning Trajectories;
- repeated representation findings;
- validated lesson hypotheses;
- durable domain knowledge;
- research conclusions.

Do not dual-write every learner micro-event to FOSSIL and do not make resume/checkpoint depend on FOSSIL availability.

## Backup/recovery

Before valuable longitudinal data accumulates, implement:

- DB backup/export;
- private evidence-store backup;
- integrity/hash verification;
- restore test.

Invariants:

- deleting FOSSIL must not destroy Study OS;
- losing graph/search projections must not destroy learner evidence;
- losing a derived checkpoint must not destroy underlying events/raw evidence.

## Build sequence

### L0 — local storage foundation
- [ ] project-agnostic SQLite schema + migrations
- [ ] private evidence store
- [ ] repository/service layer
- [ ] `doctor` / health validation
- [ ] DB + evidence backup/export/restore
- [ ] local canonical checkpoint/resume

### L1 — MCP semantic boundary
- [ ] semantic MCP tools
- [ ] strict tool schemas
- [ ] auth assumptions
- [ ] deterministic fixture/integration tests

### L2 — ChatGPT integration
- [ ] package unified Study OS custom app/plugin surface
- [ ] connect WSL MCP through Secure MCP Tunnel or equivalent safe private path
- [ ] verify current ChatGPT plan/workspace supports required read/write actions
- [ ] verify `@StudyOS status`
- [ ] verify `@StudyOS resume`
- [ ] verify event/assessment writes
- [ ] verify `@StudyOS checkpoint`
- [ ] verify fresh Chat A -> checkpoint -> fresh Chat B resume continuity

### L3 — automatic instrumentation after R0
- [ ] automatic meaningful event capture
- [ ] boundary-triggered checkpoint proposals
- [ ] retention automation
- [ ] richer mobile UI
- [ ] Postgres/object-store migration only if justified

## Acceptance principle

The learner should be able to focus on learning. The tutor/agent chooses how to teach; the Study OS service owns persistence, scoring, provenance, checkpointing, versioning, and validation. GitHub hosts the product/research source, not the live learner database.
