# Issue #160: Tutor reply latency is 18-60s+ on live — ack fix makes it survivable, not fast

- State: open
- Opened by Pukujan on 2026-09-27
- Original: https://github.com/Pukujan-lab/Study-os/issues/160

## Observed

While verifying the A13 chat-ack fix (#126, PR #156/#159) on live, the tutor round-trip was measured three times at 1440x900:

| Run | Time to ack | Time to reply |
|---|---|---|
| 1 | 71 ms | 33,328 ms |
| 2 | 57 ms | **never arrived within 60,000 ms** |
| 3 | 57 ms | 18,115 ms |

Prompt in all three: `What should I notice on this step?` on the HESI comparing-fractions player, guest session, `POST /api/player/sessions/{id}/tutor`.

## Why this is its own issue

The A13 defect was *no observable change while in flight*. That is fixed — the ack now lands in ~60 ms, so the learner always sees the app is working. But the reply itself taking 18-60s+ is a different problem: the ack makes the latency survivable, not solved. A learner waiting a minute for "what should I notice" is a product failure independent of the ack.

## Not yet diagnosed

Unknown from this evidence alone:
- which provider/model served these calls, and whether a fallback fired
- whether latency is provider-side, prompt-size, or the validate→repair loop
- whether the >60s run 2 timed out client-side or is still in flight

## Evidence class

`observed` — three live runs, real tutor round-trip, DOM + network timings.

## Suggested next step

Instrument the tutor call (provider, model, attempt count, time-to-first-token vs total) on the live path, then re-measure. Do not guess at a fix before that.
