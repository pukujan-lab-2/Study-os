## Purpose

Converge Study OS's durable curriculum architecture, proficiency/tier semantics, and daily study-planning method without broadening live adaptive authority or prematurely instantiating a full Python->ML->AI course.

Parent/related trackers:
- #3 — durable v0.1 DSA interaction + proficiency/tier specification;
- #10 — canonical learner/curriculum/adaptive implementation tracker;
- #21 — verification prerequisite for learner-control semantics before G5+;
- #26 — canonical application boundary; transport/frontend work must consume rather than redefine these semantics.

This issue is **curriculum/control-plane design and staged implementation planning**, not authorization to add HTTP/frontend work, change the exact 13-tool MCP surface, or give an adaptive component live authority.

## Problem to resolve

Study OS currently has two different concepts using overlapping `T*` naming:

1. #3 defines DSA proficiency tiers `T0`–`T6` (Orientation -> Interview Ready -> Advanced).
2. `docs/LEARNING_CONTROL_MODEL.md` defines planned competency tracks `T1`–`T5` (algorithmic, software/systems, system design/reliability, AI systems, technical diagnosis).

These are not the same dimension. The collision must be removed before the curriculum expands.

Study OS also has strong primitives for capability state, assistance, task complexity, representation effectiveness, retention and episode progression, but no canonical daily-goal method or unified learner study-plan schema yet.

## Durable distinctions

Do not collapse these dimensions:

- **track** — what competency family is being developed;
- **competency/capability** — observable behavior being assessed;
- **capability state** — `not_tested`, `fail`, `partial`, `pass_supported`, `pass_unaided`, `pass_transfer`, `pass_delayed`;
- **assistance** — A0–A6;
- **task/operation difficulty** — existing multidimensional complexity plus L0–L10 learning-operation ladder where applicable;
- **representation effectiveness** — contextual intervention evidence, not learner mastery;
- **proficiency tier** — repeated cross-item/session capability gate, never a one-problem promotion;
- **daily study goal** — a revisable evidence-collection plan, not learner truth.

## Curriculum architecture direction

Retain the current research-first scope while defining a broader future track map. Proposed architecture to review in the design PR:

- `ALG` — Python fluency, manual implementation, DSA, complexity, debugging, transfer;
- `SWE` — Git, modules, typing, testing, APIs, SQL/databases, concurrency, software design;
- `MATH` — algebra, linear algebra, probability/statistics, calculus/optimization as needed;
- `DATA` — NumPy, pandas, visualization/data handling;
- `ML` — classical ML, training/evaluation, leakage, baselines, calibration/error analysis;
- `DL` — PyTorch, neural networks, optimization, embeddings, attention/transformers;
- `AIE` — LLM APIs, structured outputs, tools, RAG/retrieval, evals, workflows/agents;
- `SYS` — production engineering, reliability, model serving, caching/queues, distributed/system design;
- `DIAG` — technical problem framing, debugging, evidence acquisition, hypothesis testing and communication.

This architecture is not a claim that all tracks are active or validated. Current R0 scope remains narrow and explicit.

## Proficiency/tier reconciliation

Preserve #3's existing DSA tier semantics but rename/namespace them so they cannot be confused with curriculum tracks. The design PR should choose a stable namespace (for example `DSA0`–`DSA6` or an equivalent explicit proficiency prefix) and provide compatibility language for old `T0`–`T6` prose.

Do not invent one universal tier scale for every future track until the evidence requirements for that track are defined. SWE/ML/AI proficiency may need different gate dimensions even if a UI later presents comparable bands.

DSA promotion continues to require repeated evidence across problems/sessions and must include relevant unaided implementation, transfer and delayed-retention evidence; averages cannot hide a critical implementation/transfer bottleneck.

## Daily study-goal model

Do **not** implement a calendar/quota scheduler first. Define a small evidence-goal abstraction whose purpose is to answer:

> Given canonical learner evidence, due retention, current phase, explicit learner priorities and available study budget, what is the highest-value bounded evidence objective for this study session/day?

Initial advisory shape should be capable of expressing:

- goal/plan version;
- target track + competency;
- current capability state/evidence refs;
- desired next evidence state;
- task/interaction mode;
- maximum assistance / fade target;
- due retention obligations;
- transfer probe if warranted;
- explicit priority or interview need;
- optional time/effort budget as a planning constraint, never mastery evidence;
- stop/replan condition;
- rationale/provenance.

Daily goals are **derived/advisory plans**, not observed evidence and not canonical mastery state.

## Initial daily-loop policy

A simple deterministic/advisory loop is preferred before optimization:

`due retention -> highest-value active competency -> diagnose if ambiguous -> practice/remediate -> fade -> transfer if warranted -> checkpoint -> schedule next probe`

Do not use arbitrary quotas such as "5 problems = progress" as the core advancement rule. Time spent and item count may be operational constraints/telemetry, but progression is evidence-gated.

## Manual vs AI-assisted evidence

Use existing interaction-mode + assistance provenance to distinguish evidence collected under materially different conditions. Do not let AI-assisted success silently count as unaided manual implementation.

Examples that must remain distinguishable:
- blank manual coding;
- scaffolded manual coding;
- code reading/debugging;
- AI oversight/review;
- AI-assisted construction;
- verbal/phone shorthand where full implementation is not being measured.

A future view may compare manual and AI-augmented capability, but canonical evidence should remain task/assistance-specific rather than fabricating one global dual score.

- update curriculum architecture docs and issue cross-links;

- define daily evidence-goal semantics and non-goals;

### C1 — proficiency-gate specification
- formalize DSA repeated-evidence promotion matrix from #3 against canonical capability states/A0–A6/transfer/retention;
- define negative cases preventing one-item, supported-only, self-report-only or average-score promotion;
- keep result read-only/advisory until verified.

### C2 — learner-state prerequisites
Depends on #10 richer `LearnerSnapshot` work, especially:
- capability evidence refs;
- current/last successful assistance;
- active goals/current phase;
- recent exposure summary;
- interaction/device/tool constraints where relevant;
- explicit next fade target / next high-information action.

### C3 — shadow daily-goal selector
After C2, implement deterministic baseline planning and any candidate adaptive planner behind the existing `LearnerSnapshot -> DecisionProposal -> shadow/audit` envelope.

Require replay/differential/property verification appropriate to touched semantics. No live authority.

### C4 — real learning validation
Use real R0/R1/G4 trajectories to determine whether the daily-goal policy improves evidence collection and learner continuity. Compare planned objectives to downstream unaided/transfer/delayed outcomes.

### C5 — bounded advisory/live authority later
Only after relevant #21 E5–E7 verification and #10 promotion gates. Add explicit accept/reject logging + kill switch before any planner can own bounded live selection.

## Curriculum expansion rule

Do not instantiate hundreds of lessons/items now. Keep broad architecture durable, then add narrow atomic slices only after the existing measurement/control loop demonstrates trustworthy behavior per #10.

Near-term instantiated learning should prioritize the current manual-Python/DSA objective and existing R0 evidence loop. Math/data/ML/DL/AIE tracks can be mapped structurally now and instantiated incrementally when goals/prerequisites justify them.
