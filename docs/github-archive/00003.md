## Purpose

This issue is the executable v0.1 learning interaction spec for Study OS.

Study OS v0.1 is **not** a full DSA course or coding IDE. It is a mobile-first, instrumented learning loop for Subject 001 that detects where understanding breaks, changes representation/operation, measures whether the intervention worked, fades assistance, and checkpoints the learner state for cross-session continuation.

Related issues:
- #1 — initial Study OS DSA learning harness
- #2 — research gate and thesis validation

## v0.1 scope

- Subject: `subject-001`
- Domain: DSA
- Language: Python
- First concept family: Sliding Window
- Primary surface: phone-friendly conversational tutoring
- Secondary validation surface: laptop/keyboard when full implementation is appropriate

## Core interaction loop

When the learner says something like:

> “I don’t understand this question. Can you explain it differently?”

that is **not scored as failure/mastery loss**. It creates a comprehension/diagnostic event.

The tutor should localize the bottleneck through the smallest useful probe:

`problem wording -> recognition -> mental model -> state -> invariant -> procedure -> pseudocode -> Python -> debugging -> transfer`

Possible response sequence:

1. restate the task concretely;
2. show a small example;
3. switch representation if needed;
4. ask a prediction/explanation question;
5. observe whether the learner succeeds;
6. fade/remove the representation;
7. retest;
8. later test changed-surface transfer and delayed retention.

The tutor must not reveal the full solution merely because the learner reports confusion.

## Initial representation families

- concise prose / causal explanation;
- concrete worked example;
- static array/pointer figure;
- Mermaid flowchart;
- graph/tree/dependency representation where appropriate;
- deterministic state trace;
- invariant / rule-that-remains-true;
- semantic procedure;
- pseudocode;
- Python scaffold;
- blank Python implementation;
- later: validated audio/video/image representations.

## Representation operations

Record the operation separately from modality:

- restate
- expand
- decompose
- trace
- predict
- explain
- contrast
- abstract
- specialize
- translate
- reconstruct
- debug
- fade
- transfer

Example: `deterministic_state_trace + predict` is different from `deterministic_state_trace + passive_observe`.

## Representation-effectiveness scoring

Do **not** assign one universal score like “Mermaid = 90%.”

Score effectiveness contextually by:

`subject × concept × bottleneck × representation × operation × version`

Initial evidence scale:

- **0 — ineffective:** confusion unchanged/worse or behavior deteriorates;
- **1 — self-report only:** learner says it helped but no behavioral test yet;
- **2 — supported immediate success:** correct response while representation/scaffold is visible;
- **3 — faded success:** correct after the representation/scaffold is removed;
- **4 — transfer success:** correct on a changed/unseen surface problem;
- **5 — retained success:** correct again after a delayed interval.

Self-report must remain separate from the effectiveness evidence score.

## Learner capability model

Do not collapse learner state into one mastery number.

Track at minimum:

- problem comprehension;
- pattern recognition;
- mental model/explanation;
- state tracing/prediction;
- invariant reasoning;
- semantic procedure/pseudocode;
- Python implementation;
- debugging;
- complexity reasoning;
- transfer;
- delayed retention;
- assistance/hint dependence.

A dashboard may later compute a composite score, but tier advancement uses capability gates rather than averages alone.

## DSA tier model

### T0 — Orientation
- basic problem comprehension;
- arrays/variables/loops can be traced with support;
- no independent DSA expectation.

### T1 — Guided Easy
- recognize common patterns from constrained options;
- predict simple state changes;
- explain simple algorithms;
- arrange code/procedure steps;
- complete scaffolded Python.

### T2 — Independent Easy
- solve unseen Easy-type problems with minimal/no hints;
- identify pattern without multiple choice;
- explain invariant;
- reconstruct semantic pseudocode;
- implement basic solution;
- debug basic errors.

### T3 — Guided Medium
- solve Medium-type problems with small cues/visual support;
- produce most of the algorithm independently;
- assistance is measurable and fading.

### T4 — Independent Medium
- repeatedly solve unseen Medium-type problems;
- recognize pattern, derive procedure, implement, debug, and explain complexity without scaffolding.

### T5 — Interview Ready
- mixed topics;
- unseen problems;
- limited hints;
- communication under time constraints;
- retention across sessions;
- consistent Medium performance plus selected harder variants.

### T6 — Advanced
- combine patterns;
- derive modifications;
- optimize alternatives;
- reason about difficult invariants;
- tackle Hard-type problems.

Tier advancement requires repeated evidence across problems/sessions and must not be triggered by one successful problem.

## Difficulty is multidimensional

Do not equate difficulty only with Easy/Medium/Hard.

Study OS difficulty is a product of:

`problem difficulty × assistance level × cognitive operation × novelty × time constraint`

An Easy problem from a blank editor may currently be harder than a Medium problem with a visual multiple-choice trace.

## Mobile-first interaction ladder

Phone study must train real algorithmic reasoning without pretending a touchscreen is a good desktop IDE.

### M0 — Observe
View a deterministic state/figure.

### M1 — Multiple choice recognition
Choose likely pattern/next state.

### M2 — Constrained discrimination
Choose among similar plausible answers.

### M3 — Manipulation / ordering
Order algorithm steps, pointer moves, queue operations, etc.

### M4 — Fill-the-gap
Fill missing variable/operator/code fragment.

### M5 — Short production
Write one line or a small code block.

### M6 — Verbal explanation
Explain state/invariant/procedure in own words, including voice when available.

### M7 — Reconstruct without representation
Describe or rebuild the process after visual support is removed.

### M8 — Full implementation
Use laptop/keyboard or a practical coding surface for blank implementation and execution.

Mobile evidence counts toward learner state. Laptop validation is used for dimensions that genuinely require complete executable code.

## Mobile example

Instead of requiring 30 lines of Python on a phone:

```text
Current window: [2, 1, 5]
sum = 8
limit = 7

What happens next?
A. Move right
B. Move left
C. Reset
D. Sort
```

Then fade choices:

1. choose answer;
2. choose among similar answers;
3. arrange operations;
4. fill missing variable;
5. write one line;
6. explain in own words;
7. reconstruct without visual;
8. later perform full implementation.

The purpose is accessibility without permanently reducing the learner to recognition-only tasks.

## Promotion / next-tier gate

A concept/tier promotion should require a configurable repeated-evidence threshold, initially including:

- multiple unseen problems;
- more than one session when practical;
- pattern recognition without choices;
- correct state tracing;
- invariant/procedure explanation;
- pseudocode reconstruction;
- implementation evidence where relevant;
- hints below threshold;
- changed-surface transfer;
- delayed retention.

Do not require every axis to be perfect, but do not allow a high average to hide a critical bottleneck such as implementation or transfer.

## Checkpoint/resume integration

At session end or meaningful learning boundaries:

- persist current tested capabilities;
- persist representation outcomes;
- persist assistance/fading state;
- persist unresolved hypotheses;
- record what should not be retaught;
- record the next highest-information probe;
- update `subjects/subject-001/CURRENT.json` through the checkpoint contract.

A fresh chat/model should be able to continue from the latest accepted checkpoint rather than full transcript memory.

## FOSSIL boundary

FOSSIL is **not** required for this interaction loop or checkpointing.

Study OS owns high-frequency learner events and state. FOSSIL may later receive promoted durable artifacts such as:

- curated Golden Learning Trajectories;
- repeated representation findings;
- validated lesson hypotheses;
- external research conclusions;
- durable DSA concept knowledge.

## v0.1 acceptance criteria

### Interaction
- [ ] “I don’t understand” produces a diagnostic event rather than a mastery penalty.
- [ ] Tutor can switch between at least 4 deterministic/structured representations.
- [ ] Tutor records representation family + operation + version.
- [ ] Tutor asks behavioral probes after interventions.
- [ ] Tutor supports fading/removal of help.

### Scoring
- [ ] Learner capability dimensions stored separately.
- [ ] Representation-effectiveness evidence score 0–5 implemented or manually recordable.
- [ ] Assistance level recorded.
- [ ] Tier progression uses gates rather than one average score.

### Mobile
- [ ] recognition/choice interaction;
- [ ] state prediction;
- [ ] step ordering;
- [ ] fill-the-gap;
- [ ] short code production;
- [ ] verbal/plain-language explanation;
- [ ] scaffold fading;
- [ ] laptop/full-code validation path.

### Longitudinal
- [ ] first baseline learning episode recorded;
- [ ] first representation switch recorded;
- [ ] first immediate faded retest recorded;
- [ ] first accepted learner checkpoint created;
- [ ] next fresh session successfully resumes from checkpoint;
- [ ] changed-surface transfer tested;
- [ ] delayed retention tested;
- [ ] first Golden Learning Trajectory assembled.

## Start condition

We can begin the **first baseline learning session immediately** once this issue exists. No production UI, plugin packaging, FOSSIL runtime, generated video, or full curriculum is required for the first experiment.

The first session should begin with a Sliding Window baseline that avoids teaching the answer before we observe where Subject 001 actually gets stuck.
