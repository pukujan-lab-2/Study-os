# Issue #86: [WebApp] Auth and accounts: Google sign-in with open signup, local email/passphrase fallback, minimal profile

- State: open
- Opened by Pukujan on 2026-09-24
- Original: https://github.com/Pukujan-lab/Study-os/issues/86
- Labels: enhancement

## Why this matters
There are two real learners now and maybe beta users later. Accounts must separate their data without collecting personal data.

## Outcome
App-managed auth on the backend:
- invite code → pseudonymous handle + passphrase (argon2id);
- server-side sessions in an httpOnly, Secure, SameSite=Lax cookie on the API host;
- Origin and CSRF-header checks;
- roles `learner` and `admin`;
- `account_id` maps to a pseudonymous `subject_id`, and learning tables only see `subject_id`;
- phase 2 adds passkeys (WebAuthn);
- no email is stored, and there is no third-party identity provider.

The admin surfaces (Metabase, admin API) stay reachable only on the tailnet or behind Cloudflare Access.

## Acceptance criteria
- [ ] The accounts table holds only handle, passphrase hash, role, and timestamps. A schema test fails if columns such as email, name, or phone are added.
- [ ] Cross-account access is denied by a row-level ownership check. A property test covers randomized account/session pairs.
- [ ] Session revocation and passphrase reset by an admin work without email.

**Pukujan commented, 2026-09-24**

**D018 (owner amendment to D017, 2026-09-24):** open signup replaces invite-only. Google sign-in (OIDC authorization code with `state` + PKCE S256 + nonce) is primary; it activates when `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are in `/srv/study-os/.env`. A local email/passphrase fallback (argon2id) serves dev and use before Google keys exist. Minimal profile only, in `auth.*`: Google subject, email, display name, learner handle; learning tables still see only the pseudonymous `subject_id`. Server-side sessions in Postgres; HttpOnly Secure SameSite=Lax cookie; 30-day absolute and 7-day idle expiry; CSRF token header + Origin check on mutations. Local login throttling: 5 failed attempts per 15 min per account and 20 per IP, with exponential backoff. Per-user daily cap on LLM/Jev calls, a global daily spend cap, and per-IP/per-user request rate limits. The acceptance item 'accounts table holds only handle…' is superseded by an allowlist test for exactly these profile columns. Implemented in SOS-0004 (#99).
