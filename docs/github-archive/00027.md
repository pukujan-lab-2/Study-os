# Issue #27: [Not planned now] SWE/platform gaps before HTTP/frontend slices

- State: closed (2026-09-03)
- Opened by Pukujan on 2026-08-25
- Original: https://github.com/Pukujan-lab/Study-os/issues/27

## Purpose

Close the remaining software-engineering/platform foundations that are easy to postpone while the Python semantic runtime is small but become expensive once application-contract, HTTP, generated-client, and frontend vertical slices exist.

Parent trackers: #21 production-grade verification/SWE foundations, #26 canonical application contracts/frontend assurance, #10 P2 learner/adaptive integration.

This issue does **not** authorize HTTP/frontend implementation and does not change the 13-tool semantic boundary. It is a closure checklist so future adapters/UI inherit stable build, module, version, configuration, security, and release rules rather than inventing them per slice.

## Gate placement

### F0 — before #26 E11a behavior-moving contract extraction

Required or explicitly ratcheted with a documented plan:

- repository merge governance/required checks;
- reproducible Python build/install and supported-runtime matrix;
- formatter/lint/type baseline strong enough to survive module extraction;
- dependency lock/update/security policy;
- module ownership/dependency map;
- configuration/time/ID semantics that application contracts can rely on;
- clean-checkout bootstrap verification.

### F1 — before E11b HTTP exposure

Additionally require:

- explicit runtime configuration/secrets contract;
- transport auth/threat-model prerequisites from #26;
- safe structured observability/correlation;
- packaging/release artifact discipline;
- supply-chain checks appropriate to an exposed service.

### F2 — before E11c/E11d TypeScript client/frontend

Additionally require:

- one JS/TS workspace/package-manager policy + lockfile;
- strict TS/lint/format/build/test baseline;
- package/import boundaries preventing UI ownership of application semantics;
- generated-client freshness/build enforcement;
- browser bundle/source-map/third-party dependency policy;
- #26 frontend/measurement-validity gates.

## S0 — repository governance / merge integrity

- [ ] protect `main` with required current-head CI checks/ruleset; routine merges cannot bypass verification
- [ ] disallow force-push/deletion to `main` except explicit administrative recovery policy
- [ ] define PR review/ownership expectations for behavior-bearing paths
- [ ] add CODEOWNERS or equivalent path ownership once multiple ownership zones exist (`contracts`, migrations, application semantics, transports, frontend, workflows)
- [ ] require conversation resolution/review where repository settings support it and the project warrants it
- [ ] document emergency rollback/bypass procedure separately from normal merge flow

Current observed gap: `main` is presently unprotected; CI exists but GitHub does not enforce it server-side.

## S1 — reproducible build/install/runtime matrix

- [ ] choose one reproducible dependency-lock mechanism for Python runtime + dev/test dependencies
- [ ] build wheel + sdist in CI from a clean checkout
- [ ] install the built artifact into a fresh environment and run import/CLI smoke; tests must not rely accidentally on repository-root import behavior
- [ ] test every Python minor version the package claims to support, initially 3.11 and 3.12 while `requires-python >=3.11`
- [ ] define runtime vs dev/network extras deliberately; optional transports must not leak into the semantic core
- [ ] fresh-checkout bootstrap command/documentation reproduces lint/type/test/build without private credentials
- [ ] generated/build artifacts are reproducible or have deterministic freshness/hash checks where bit-for-bit output is impractical

## S2 — static quality ratchet

- [ ] Ruff format check in CI
- [ ] broaden Ruff rules beyond critical syntax/import failures using a reviewed rule set; do not mass-disable categories to get green
- [ ] define a Pyright ratchet from current `basic` toward strict-enough per-module enforcement
- [ ] no blanket `Any`/ignore growth in contract/application boundaries without explicit reason
- [ ] type-check tests/tools or selected critical tooling where it materially catches boundary drift
- [ ] architecture/static checker validates dependency cycles and allowed layer direction, not only adaptive/curriculum forbidden imports
- [ ] any baseline suppression has owner/reason/expiry or is encoded as a narrow intentional exception

## S3 — dependency / supply-chain / security baseline

- [ ] dependency vulnerability scanning in CI/scheduled cadence
- [ ] CodeQL/SAST where applicable
- [ ] secret scanning/pre-commit or CI detection for committed credentials/tokens/private keys
- [ ] automated dependency-update mechanism (Dependabot/Renovate/equivalent) with CI verification; no blind auto-merge of behavior-affecting upgrades
- [ ] pin GitHub Actions to reviewed immutable SHAs or document an equivalent trusted update policy
- [ ] record direct dependency licenses and add transitive license/SBOM policy before distribution/product packaging
- [ ] produce an SBOM/release dependency manifest when distributable artifacts/frontend bundles exist
- [ ] donor/library provenance from #10 remains separately recorded from generic package supply-chain metadata

## S4 — runtime configuration / secrets contract

Before multiple adapters exist, define one configuration boundary:

- [ ] documented allowed environment variables/config fields and precedence
- [ ] startup validation fails closed on malformed/incompatible config
- [ ] configuration values that affect semantics are versioned/fingerprinted where replay requires them
- [ ] secrets are references/runtime inputs, never embedded in canonical contracts, generated clients, OpenAPI, fixtures, logs, examples, or browser code
- [ ] separate semantic config from deployment/local-machine config
- [ ] no repository-side change to local-only Cloudflare/WSL/GPT Action credentials/deployment files as part of foundation work
- [ ] safe sanitized config snapshot can be included in verification receipts without exposing secrets

## S5 — module ownership + dependency direction

Create and enforce a module map before central runtime decomposition. Target semantics:

```text
domain
  <- application contracts/use-cases
  <- adaptive + curriculum pure logic where applicable
  <- persistence/evidence adapters through explicit ports
  <- MCP/HTTP/CLI transport adapters
  <- generated client
  <- frontend presentation slices
```

The exact package layout can differ, but dependencies must point inward toward owned semantics.

- [ ] module ownership/responsibility map names authoritative owner for each invariant
- [ ] application/use-case layer has explicit ports/interfaces for persistence/evidence needs rather than importing transport/UI concerns
- [ ] persistence adapters cannot become application policy owners
- [ ] transport adapters only translate/authenticate/shape transport and invoke application use cases
- [ ] no MCP/HTTP route/controller owns learner-state/checkpoint/adaptive rules
- [ ] frontend may import generated client + frontend-safe presentation utilities only; it cannot import backend semantic implementation
- [ ] dependency-cycle test covers all production packages
- [ ] avoid a generic `shared/utils` dumping ground; cross-cutting packages require a defined stable responsibility
- [ ] vertical frontend slices may own presentation state/components for their feature, while server/application state remains canonical

## S6 — time, timezone, IDs, randomness, ordering

These become cross-client bugs if left implicit.

- [ ] canonical durable timestamps are UTC with explicit serialization rules
- [ ] timezone/localization is a presentation/input-edge concern; UI display timezone never changes canonical event ordering
- [ ] define which client timestamps are advisory telemetry vs server-authoritative receipt/order timestamps
- [ ] use injectable/test clock for time-bound retention/application logic where practical
- [ ] DST, timezone-boundary, clock-skew, background/suspend cases are covered before browser timing evidence is trusted
- [ ] stable ID formats/ownership are documented; clients cannot manufacture privileged authority merely by choosing an ID
- [ ] deterministic tests control UUID/random/clock sources where exact replay depends on them
- [ ] random/adaptive algorithms record seed/config/version where reproduction requires it

## S7 — fixtures/test-data discipline

- [ ] sanitized fixture builders/factories centralize valid canonical objects rather than copy/paste magic dictionaries
- [ ] fixtures declare schema/contract/version they represent
- [ ] generated/schema-validated fixtures are reused across Python/MCP/HTTP/TS conformance where appropriate
- [ ] private learner evidence and hidden answer material never enter public/browser fixtures
- [ ] deterministic clocks/IDs/seeds make stateful failures reproducible
- [ ] minimized Hypothesis/mutation/chaos failures become named regression fixtures when they expose a real defect

## S8 — release/version/migration discipline

- [ ] define release/tag/changelog or release-note policy for behavior/contract changes
- [ ] keep runtime package version distinct from DB/MCP/application-contract/curriculum/telemetry/adaptive versions per #21 E12
- [ ] compatibility matrix states supported application/API/client versions once E11a exists
- [ ] migrations are forward-tested from supported prior DB states and rollback/recovery expectation is explicit
- [ ] backup/restore compatibility is tested before destructive migration/release paths
- [ ] release receipts identify exact source SHA, dependency lock, contract/schema versions, checks run, and generated-artifact versions
- [ ] rollback procedure identifies code + schema/contract constraints rather than assuming code-only rollback is safe

## S9 — observability / diagnosability foundation

Before HTTP/frontend workflows depend on remote failures:

- [ ] stable request/operation correlation ID that can cross transport -> application -> persistence without becoming semantic authority
- [ ] structured logs with stable event/error categories where useful
- [ ] log/redaction policy excludes secrets/private evidence/hidden answers and avoids raw sensitive payload dumping
- [ ] health/readiness semantics distinguish process alive from runtime integrity where applicable
- [ ] metrics/telemetry are observational and do not become learner truth
- [ ] exact durable write result can be reconciled after client timeout/unknown result using canonical identifiers/idempotency semantics
- [ ] define retention/deletion policy before broad client telemetry is enabled

## S10 — TypeScript/frontend toolchain baseline (activate only when E11c/E11d starts)

- [ ] choose one package manager/workspace strategy; commit the lockfile
- [ ] strict `tsconfig`; no routine unchecked `any` at contract boundaries
- [ ] lint + deterministic format gate
- [ ] production build gate and bundle-size observation/budget once measured
- [ ] unit/component harness + Playwright E2E baseline
- [ ] generated client lives in a framework-neutral package; React/Svelte code consumes it rather than wrapping a second hand-authored API model
- [ ] frontend package dependency rules mechanically prevent reverse imports into generated contracts/application semantics
- [ ] browser artifact scan for secrets/hidden answers/server-only grader material
- [ ] CSP/XSS-safe rendering policy and no unreviewed third-party executable script dependency
- [ ] source-map publication policy prevents accidental secret/hidden-fixture disclosure
- [ ] framework-specific state stores may cache/present server state but never become canonical learner/checkpoint authority

## S11 — CI topology / cadence

Keep CI layered rather than one giant job:

**Per PR:** format/lint/type/build, project/schema/version/architecture drift, focused unit/contract/property, package-install smoke, generated freshness, relevant adapter/UI smoke.

**Main/post-merge:** supported-runtime matrix, broader differential/integration, artifact build/install, compatibility matrix.

**Scheduled/nightly:** dependency/security/license sweeps, broader Hypothesis/fuzz/mutation, retry/fault matrix, browser matrix once UI exists.

**Release:** exact-SHA clean-environment receipt, compatibility/migration/backup, critical E2E, security/privacy, generated artifacts/SBOM, rollback readiness.

Do not block every small PR on every expensive assurance method; use #21 risk/failure-model cadence.

## Acceptance / relationship to #21 and #26

This issue augments rather than replaces #21/#26:

- #21 remains the master assurance/checklist and owns E0-E12 verification architecture.
- #26 owns canonical application-contract and frontend-specific verification/measurement validity.
- this tracker owns closure of platform/repository/build/release foundations that should be stable before those layers multiply.

Before closing this issue, each checkbox must be either implemented with evidence or explicitly deferred to F1/F2 with a named dependency and reason. A prose claim that something is 'production ready' is not closure evidence.

## Non-goals

- no frontend implementation now;
- no HTTP/API exposure merely to satisfy this checklist;
- no microservices split;
- no speculative Kubernetes/cloud platform;
- no weakening semantic/property/integrity tests to satisfy tooling;
- no local/private credential or deployment mutation.
