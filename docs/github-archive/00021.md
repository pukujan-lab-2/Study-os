# Issue #21: [Superseded by #52] Production-grade agentic verification and SWE foundations

- State: closed (2026-09-03)
- Opened by Pukujan on 2026-08-25
- Original: https://github.com/Pukujan-lab/Study-os/issues/21

## Purpose
Establish the production-grade verification architecture for agent-authored Study OS changes. This tracker is orthogonal to #10: #10 owns learner/adaptive behavior; #21 owns whether the implementation, verifier, docs, and promotion evidence are trustworthy.

## Core principle
No single oracle is sufficient:

`spec -> static checks -> unit/contracts -> properties/state machines -> integration/E2E -> hidden holdout -> mutation/negative controls -> model/differential checks -> load/fault simulation -> targeted formal methods -> post-merge observability`

## Current repository reality

Current CI only runs Python compile, repository/schema/contract validation, and the unittest suite. The repo does not yet have Ruff, Pyright/mypy, coverage thresholds, architecture-boundary tests, Hypothesis stateful/property testing, mutation testing, hidden engineering holdouts, a reference-model differential harness, load/chaos simulation, or formal-model CI.

The codebase is a modular-monolith-in-progress. `adaptive/` is already decomposed; semantic runtime behavior remains concentrated behind `services/runtime.py` + a large preserved `services/runtime_base.py`. Do not aggressively refactor that runtime until stronger independent behavioral oracles exist.

## E8 — integration/E2E/load verification

- [ ] realistic concurrent/retry workload when meaningful

## E9 — chaos/failure injection
- [ ] process kill/restart at transaction boundaries
- [ ] DB locked/busy + retry storms
- [ ] disk-full/write/permission failure for DB/evidence/export/backup
- [ ] evidence missing/corrupt/hash mismatch
- [ ] network delay/disconnect/timeout/duplicate/reordered requests
- [ ] clock-skew/time-boundary retention cases
- [ ] interrupted backup/restore/external dependency failures
- [ ] define steady-state invariants; chaos only in disposable environments

## E10 — targeted formal methods
Use only where the modeled failure class warrants the cost.
- [ ] TLA+ for checkpoint/current-pointer/idempotency/retention/concurrency protocols if state-space complexity justifies it
- [ ] Alloy/SAT-style checks for prerequisite DAGs/relational structural invariants
- [ ] SMT/Z3/Dafny-style checks for bounded deterministic constraints when executable properties are insufficient
- [ ] theorem proving reserved for tiny high-value core semantics
- [ ] any formal model must be connected back to production through differential/random tests
- [ ] formal verification includes intentional violating negative controls

## E11 — modular monolith foundations
Target direction:

`domain/contracts -> curriculum + adaptive pure logic -> application/use-cases -> persistence/adapters -> MCP/HTTP/CLI`

- [ ] module ownership/responsibility map
- [ ] adaptive/curriculum pure logic cannot reach SQLite/network/filesystem directly
- [ ] transport adapters cannot implement semantic persistence rules
- [ ] central runtime facade decomposed only after behavior is protected by E3/E4
- [ ] architecture tests fail forbidden imports/dependency cycles

Suggested eventual test layout:

```text
tests/
  unit/
  contract/
  property/
  stateful/
  integration/
  e2e/
  simulation/
  chaos/
formal/
protected holdout outside coding-agent-visible public context
```

## E12 — version/provenance discipline
- [ ] one runtime/package release version
- [ ] independent versions only for persistent/external semantics: DB schema, MCP/API contract, JSON schemas, curriculum/items, telemetry, adaptive algorithm/policy, formal model
- [ ] every persisted adaptive proposal/result records component id/version + relevant config/hash + input snapshot version
- [ ] dependencies reproducibly locked; donor/library version recorded
- [ ] compatibility/migration tests for schema/contract upgrades

## Verification cadence

**Every PR:** E0 static/version/architecture baseline + focused unit/contract/property tests + relevant hidden acceptance.

**Main/post-merge:** broader integration/replay/reference-model differential.

**Nightly/scheduled:** large property/stateful exploration, mutation, fuzzing, >=100x learner simulations, dependency/security sweeps.

**Release / before live adaptive promotion:** hidden holdout, backup/restore, load/performance, selected chaos, project-state/doc convergence, exact-SHA verification receipt.

**Formal models:** only when changes touch formally modeled semantics.

## Promotion coupling to #10

#10 G0-G4 can continue with shadow/replay work. **No component advances to G5 advisory/canary or later until the relevant E0-E7 verification layers are implemented and green for that component/runtime path.**

## Immediate implementation order

1. merge manifest/handoff/current-state sync;
2. Ruff + Pyright + coverage + version/doc/architecture checks;
3. Hypothesis semantic properties/state machine;
4. executable reference model + differential harness;

## Non-goals
- Do not adopt every formal tool everywhere.
- Do not treat coverage, mutation score, LLM review, simulation, or formal proof as a single sufficient oracle.
- Do not auto-commit hand-edited AGENTS/HANDOFF policy prose from CI by default.

- Do not split into microservices merely to look production-like.

## Durable architecture decision: canonical application contracts before frontend

Record this as the planned E11 architectural seam once E4 reference/differential protection is in place.

### Invariant

`domain/state -> application use cases -> canonical application contracts -> transport adapters`

MCP, HTTP and CLI are adapters. MCP tool schemas are **not** the source of truth for application semantics. Preserve the current exact 13-tool MCP semantic boundary unless a separately reviewed durable contract change explicitly alters it.

### Planned implementation order

1. finish E3 semantic property/state-machine coverage;
2. build E4 independent in-memory reference model + differential harness;
3. add E11a canonical application-contract layer before major runtime-facade decomposition;
4. keep MCP as a conforming adapter over those contracts;
5. later add an HTTP adapter over the same contracts;
6. only after product scope warrants it, add one React or Svelte client using generated framework-neutral types/client code.

### E11a scope

- explicit transport-independent request/response DTOs for application use cases;
- stable machine-readable error/result envelope and error codes;
- explicit contract/schema versioning;
- JSON Schema/OpenAPI generation where appropriate;
- generated TypeScript contract/client artifacts with freshness checks;
- adapter-conformance tests proving MCP/HTTP mappings preserve canonical outcomes;
- no duplicate learner-state, eligibility, persistence or adaptive-promotion logic in transport/frontend layers.

### Frontend authority boundary

A future frontend is an interaction/request surface only. It cannot become authority for learner state, checkpoint advancement, evidence eligibility, assistance ceilings, retention completion, adaptive promotion, hidden-holdout access, or any other semantic gate. Crafted browser/API requests must still be rejected by backend application/domain rules when unauthorized or invalid.

### Frontend verification ladder

When a frontend exists, require as applicable:

- contract-generation/freshness tests;
- generated-client type/build checks;
- component/unit tests for rendering and interaction states;
- schema-derived mock-contract integration fixtures rather than hand-maintained drift-prone fakes;
- real disposable-backend integration tests;
- Playwright browser E2E over critical flows (start/attempt/assessment/checkpoint/restart/resume/retention);
- authority-negative/bypass tests using crafted requests;
- accessibility checks plus keyboard/focus smoke;
- responsive/cross-browser smoke for the core study loop;
- visual regression only as a supplemental UI oracle, never as learner-state correctness proof.

The reference model/domain/application layers remain the primary semantic correctness oracles; frontend tests verify wiring, presentation, interaction and inability to bypass backend authority.

### Scheduling rule

Do not implement the frontend now. Implement E11a immediately after E4 and before major HTTP/UI work or aggressive runtime-facade decomposition. Continue E5-E7 assurance work afterward; HTTP/UI can be added later without rewriting semantic logic.
