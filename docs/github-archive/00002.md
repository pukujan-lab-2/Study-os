## Goal

Run a research-first phase before broad product implementation.

Study OS should test a narrow thesis:

> Can an AI-assisted learning system detect where a learner fails to translate between representations of a technical concept, change the representation/learning operation, and then demonstrate improvement through unaided performance, transfer, and delayed retention?

## Research findings that support a prototype

- Worked examples reduce unproductive search for novices; support should fade with expertise.
- Subgoal-labeled worked examples in programming can expose procedural steps experts have automated.
- Active prediction/explanation with program visualization is more defensible than passive animation viewing.
- Retrieval practice and spacing are important for durable learning.
- Structured AI tutoring can improve learning, but pedagogy cannot be delegated to a system prompt alone.
- AI-assisted programming makes foundational comprehension/debugging important because learners must evaluate and repair generated code.
- Single-case/N=1 methods can support disciplined within-person experimentation when repeated measurement and internal-validity safeguards are used.

## Findings that constrain/criticize the naive product

- Do **not** build around fixed visual/auditory learning styles; evidence does not support that matching hypothesis.
- More representations are not automatically better and can increase cognitive load/redundancy.
- Attractive algorithm visualizations may not improve learning unless the learner actively engages with them.
- Self-reported clarity does not prove mastery.
- AI can create dependency, hallucinate, or short-circuit productive reasoning.
- Subject 001 cannot establish general effectiveness.

## Subject 001 research context

Subject 001 is useful as the first design participant because the current learning problem is unusually observable:

- prior coding background centered on JavaScript;
- no completed formal Python learning sequence;
- active use of AI to create scripts/projects;
- AI-assisted ability to make code work exceeds unaided Python/DSA fluency;
- explicit goal of gaining manual code comprehension, debugging, algorithmic reasoning, and implementation skill without rejecting AI assistance;
- can report live where explanations fail and why a changed representation helps;
- willing to repeat sessions and delayed assessments.

This makes Subject 001 a strong longitudinal design participant for studying the boundary between AI-assisted productivity and internalized competence. It is not evidence of representativeness.

## Research Gate R0

Before broad UI/video/audio/multi-DSA work:

- [ ] private raw transcript evidence preserved + hashed
- [ ] normalized transcript with stable provenance
- [ ] one stable learning failure localized
- [ ] competing diagnoses probed where ambiguous
- [ ] representation + learning operation versioned
- [ ] immediate behavioral retest
- [ ] assistance faded
- [ ] changed-surface transfer test
- [ ] delayed retrieval test
- [ ] self-report compared to behavioral outcome
- [ ] experiment reconstructable by another agent from repo artifacts
- [ ] learner reports acceptable research overhead

## Core falsification stance

The project should change or stop if evidence shows that a simpler worked-example/retrieval system performs equally well, representation diagnosis is too noisy, AI dependence grows rather than fades, or instrumentation harms the learner more than it helps.
