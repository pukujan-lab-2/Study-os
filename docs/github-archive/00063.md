# Issue #63: [P4] Deterministic learning controller, representation engine, and operational improvement loop

- State: open
- Opened by Pukujan on 2026-09-04
- Original: https://github.com/Pukujan-lab/Study-os/issues/63

## Why this is now the primary product-development focus

Study OS has enough live durability and cross-session continuity to stop treating persistence infrastructure as the center of the product.

The core moat is the **learner ↔ course representation problem**:

> Course material is authored in someone else's notation, terminology, control flow, decomposition, examples, and representation. Study OS should use AI to translate that material into a representation that removes extraneous difficulty for the learner **without changing the target concept or skill**, while deterministic state and code control the curriculum path, assistance policy, progression, and evidence semantics.

The LLM is a bounded representation/generation engine. It is not the authority for curriculum progression or learner mastery.

## Core architecture

```text
COURSE / CURRICULUM GRAPH
        ↓
DETERMINISTIC COURSE STATE
        ↓
DETERMINISTIC LEARNING CONTROLLER
        ↓ authorized pedagogical operation
AI REPRESENTATION ENGINE
        ↓
LEARNER
        ↓
DURABLE OPERATIONAL EVIDENCE
        ↓
LEARNER/CONTROLLER STATE
        ↺
```

Supporting evidence substrate remains canonical:

```text
RAW / SOURCE EVIDENCE
        ↓
NORMALIZED OPERATIONAL RECORDS
        ↓
DERIVED LEARNER + SYSTEM STATE
```

## Non-negotiable authority boundary

Study OS code/state controls:

- current course node;
- prerequisite satisfaction;
- allowed next operations;
- assistance ceiling;
- whether the learner may advance;
- when assistance must fade;
- when original/source representation must be restored;
- transfer/retention scheduling where required;
- evidence/provenance semantics.

The AI may:

- generate a realization of an **authorized** operation;
- propose diagnosis hypotheses;
- transform representations under explicit constraints;
- produce explanations/examples/traces/pseudocode/code consistent with the current state.

The AI may not silently:

- advance the curriculum;
- redefine the target concept;
- claim mastery from transcript language;
- increase assistance beyond policy;
- rewrite learner state without evidence;
- replace deterministic progression rules.

## Key product hypothesis

Study OS should distinguish:

```text
TARGET / PRODUCTIVE DIFFICULTY
vs
REPRESENTATION / EXTRANEOUS DIFFICULTY
```

It should preserve the former and reduce the latter during acquisition.

Representation friction may occur at multiple levels:

- identifier/variable naming;
- terminology;
- notation;
- problem wording;
- abstraction level;
- code/control-flow style;
- index/value presentation;
- API vocabulary;
- prose vs table vs trace vs diagram vs pseudocode vs code;
- amount of context;
- decomposition / step size.

The historical `seen → index_by_num → box` sequence is an early example, but not proof of a universal learner rule.

## First-class pedagogical operations

Initial operation vocabulary should be explicit and versioned, for example:

```text
try_unaided
explain
rename_terms
change_representation
smaller_step
remove_context
expand_detail
compress_detail
show_trace
explain_invariant
give_hint
show_worked_example
restore_original
transfer_probe
retention_probe
```

Do not collapse these into a generic `tutor_response` operation.

Each intervention must record what changed. A response that both renames a variable and simplifies the task is a multi-dimensional intervention, not evidence that renaming alone caused improvement.

## Representation contract

Representations should be explicit, reversible, and evidence-linked.

Example shape:

```yaml
concept_id: dictionary_lookup
source_representation:
  identifier: seen
learner_representation:
  identifier: box
operation: rename_terms
mapping:
  seen: box
reason_evidence:
  - learner self-report of semantic interference
preserved_semantics:
  - dictionary key maps to stored value
target_difficulty_preserved:
  - dictionary lookup
extraneous_difficulty_targeted:
  - identifier interpretation
representation_version: ...
```

Acquisition should not create permanent dependence on simplified representations. Later states should deliberately restore authentic/source terminology and test robustness.

## Deterministic learner/course state machine

Initial conceptual flow:

```text
INTRODUCE
  ↓
UNAIDED_ATTEMPT
  ↓
DIAGNOSE
  ↓
AUTHORIZED_OPERATION
  ↓
REATTEMPT
  ↓
FADE_ASSISTANCE
  ↓
RESTORE_SOURCE_REPRESENTATION
  ↓
TRANSFER / RETENTION WHEN REQUIRED
  ↓
ADVANCE COURSE
```

Diagnosis can include hypotheses such as:

- missing prerequisite;
- concept failure;
- representation interference;
- task/decomposition too coarse;
- excess information/context;
- terminology/identifier interference;
- uncertain/mixed.

LLM diagnosis is **proposed/derived**. The controller decides the next allowed experiment/operation.

## Deterministic progression

Course nodes must eventually define machine-readable progression requirements rather than relying on tutor intuition.

Example:

```yaml
node: dictionary_lookup
prerequisites:
  - dictionary_literal
  - key_value_semantics
advance_when:
  - unaided_same_surface: pass
  - source_representation_restore: pass
```

Higher-value nodes may require transfer or delayed retention; trivial nodes should not be over-assessed.

## Operational transcript as product-development data

Now that real GPT turns are durably captured across sessions, normal learning is the primary improvement loop.

For every meaningful learning trajectory preserve:

```text
course node
→ learner state before
→ source representation
→ learner attempt
→ observed difficulty
→ diagnosis hypothesis
→ authorized operation
→ exact representation/intervention version
→ assistance level
→ next learner behavior
→ fade/restoration result
→ transfer/retention when applicable
```

This data should improve Study OS through **modular versioning**, not silent prompt drift.

Version independently where practical:

- course graph/version;
- controller/policy version;
- diagnosis model/version;
- operation taxonomy/version;
- representation transform/version;
- prompt/template/version;
- retrieval/version;
- assessment/version;
- learner-state derivation/version.

Every operational decision/outcome should make it possible to reconstruct which versions produced it.

## Dogfooding objective

Use Study OS continuously while progressing from current Python/DSA foundations into increasingly difficult material:

```text
basic Python / DSA
→ dictionaries / arrays / patterns
→ LeetCode-style algorithm problems
→ complex DSA
→ system design / AI-system reasoning
```

The goal is not just to finish material. It is to accumulate longitudinal evidence showing where the controller/representation engine succeeds or fails as task complexity increases.

A useful mature trajectory should demonstrate things such as:

- learner initially cannot decode/solve source material;
- Study OS identifies a plausible barrier;
- a bounded operation changes representation/decomposition;
- learner behavior improves;
- assistance fades;
- authentic/source representation is restored;
- learner handles changed problems with less/no assistance;
- later retrieval remains adequate where retention matters.

This is strong within-learner evidence. Do **not** describe N=1 longitudinal success as population-level proof.

## Expansion gate: beta/authenticated users

This is intentionally later, after meaningful longitudinal dogfooding on harder DSA/system-design topics.

Candidate gate before beta:

- live durability/continuity remains reliable;
- deterministic course/controller contracts are stable enough to audit;
- multiple versioned operational trajectories exist;
- representation operations show repeated usefulness on real tasks;
- source restoration/fading prevents permanent simplification dependence;
- major controller failure modes are known;
- evidence semantics are trustworthy.

Then add authenticated/beta users to answer a different question:

> Do the mechanisms that work longitudinally for Subject 001 generalize, need personalization, or fail for other learners?

Population expansion is validation, not an assumption.

## Long-horizon distribution/cost direction — NOT CURRENT IMPLEMENTATION

Do not make the production system depend on a large LLM for every operation forever.

As operational data accumulates, identify functions that can be replaced or front-routed by cheaper deterministic/specialized components, for example:

```text
rules/state machine
parser / AST / compiler transforms
identifier/terminology rewriting
structured templates
retrieval / cached explanations
sentence embeddings / sentence transformers
small classifiers
small local/task-specific models
IR-to-IR transforms
language/notation converters
static analysis
program traces
search/ranking
```

Possible future routing:

```text
request / learner event
        ↓
deterministic controller
        ↓
cheap deterministic transform possible? ── yes → use it
        ↓ no
retrieval/template/small model sufficient? ── yes → use it
        ↓ no
LLM required for ambiguous/generative reasoning
        ↓
result validated against operation contract
```

This is a **future distribution/economics strategy**, not a current milestone. The first objective is to discover which transformations and control decisions are actually valuable before optimizing them away from the LLM.

## Current execution plan

### P4.0 — Canonical contracts

- [ ] Define course-node contract and prerequisite/progression semantics.
- [ ] Define deterministic learning-state machine.
- [ ] Define assistance policy/levels and transition rules.
- [ ] Define first-class pedagogical-operation taxonomy.
- [ ] Define representation + reversible mapping contract.
- [ ] Define decision/provenance record linking state, operation, evidence and module versions.

### P4.1 — GPT bounded execution

- [ ] Make each learner-facing GPT teaching action originate from explicit `course_node + learner_state + authorized_operation` context.
- [ ] Prevent GPT from silently advancing course/mastery state.
- [ ] Record exact operation and representation version used for each intervention.
- [ ] Record LLM diagnosis as hypothesis rather than ground truth.

### P4.2 — Operational improvement loop

- [ ] Persist outcome records linking interventions to subsequent learner behavior.
- [ ] Support modular version identifiers for controller/representation/diagnosis/retrieval components.
- [ ] Add replay/comparison support so later module versions can be evaluated against historical evidence without overwriting it.
- [ ] Establish a small set of controller/representation quality metrics from real dogfooding.

### P4.3 — Learn through increasingly complex material

- [ ] Continue actual course use instead of synthetic product exercises.
- [ ] Capture failures/successes from real LeetCode/DSA progression.
- [ ] Extend operation taxonomy only when operational evidence warrants it.
- [ ] Test restoration to source/authentic representations.
- [ ] Extend the same control model into complex DSA/system-design learning where appropriate.

### Later — multi-user validation

- [ ] Define beta/authenticated-user architecture only after dogfooding gate is met.
- [ ] Keep learner evidence isolated by identity/tenant.
- [ ] Compare shared vs learner-specific representation policies.

### Much later — inference-cost optimization

- [ ] Profile which operations actually consume LLM inference.
- [ ] Replace high-volume deterministic transforms with code/parsers/templates where validated.
- [ ] Introduce retrieval/embeddings/small models where they preserve quality.
- [ ] Keep LLM escalation for tasks that materially benefit from generative reasoning.
- [ ] Measure cost/quality tradeoffs before changing routing.

## What is explicitly deprioritized for now

- broad frontend work;
- video generation infrastructure;
- generic multimodal platform work;
- broad population research;
- deep FOSSIL integration;
- premature multi-user/auth architecture;
- optimizing LLM cost before we know which operations matter;
- broad hardening unrelated to evidence/data/control integrity.

## Invariants

1. **Preserve target difficulty; reduce unnecessary representation difficulty.**
2. **Course progression is code/state controlled.**
3. **AI behavior is bounded by explicit authorized operations.**
4. **Source representation is restorable and eventually retested.**
5. **Raw evidence survives changes in interpretation/model versions.**
6. **Derived diagnoses are hypotheses, not truth.**
7. **Transcript language alone never becomes mastery.**
8. **Module evolution is versioned; historical evidence is never rewritten to fit a new model.**
9. **Operational learner data improves the system through replayable evidence, not hidden prompt drift.**
10. **Multi-user claims wait for multi-user evidence.**
11. **Cost optimization follows validated product behavior, not the reverse.**

## Relationship to existing work

- P3 durability/cross-chat continuity is infrastructure enabling this loop.
- Historical reconciliation remains useful because it recovers early product-discovery evidence.
- Structured public curriculum/datasets remain candidate course material.
- GPT remains the current learner-facing interface.
- FOSSIL remains optional downstream lineage/research promotion, not runtime learner-state authority.

This issue is the canonical execution tracker for the next product-development phase unless the product owner explicitly changes direction.

- `propose_auxiliary_artifact`
