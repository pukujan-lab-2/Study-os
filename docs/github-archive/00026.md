# Issue #26: [Deferred] Canonical application contracts and frontend assurance boundary

- State: closed (2026-09-03)
- Opened by Pukujan on 2026-08-25
- Original: https://github.com/Pukujan-lab/Study-os/issues/26

## Purpose

Make Study OS transport- and frontend-ready **without** building a frontend yet and without allowing MCP/HTTP/UI adapters to become owners of learner semantics.

Parent trackers: #21 engineering verification / modular-monolith foundations, #10 P2 learner/adaptive integration.

This issue is the durable execution plan for the architectural seam discussed in #21: canonical application contracts must exist between application use cases and transport adapters so a later React or Svelte client can consume the same semantics safely.

## Position in the roadmap

Do not start this implementation until:

1. the current E3 lifecycle state-machine slice is canonical on `main`;
2. #21 E4 provides an independent in-memory semantic reference model + differential harness protecting the externally meaningful runtime behavior.

Then implement E11a **before** major runtime-facade decomposition, HTTP/UI implementation, or generated frontend clients.

E11a does not replace #21 E5-E7. Mutation/negative controls, protected holdout, and seeded learner-policy simulation remain required before #10 G5+ adaptive promotion.

## Architectural invariant

```text
domain/state
    -> application use cases
        -> canonical application contracts
            -> MCP adapter
            -> HTTP adapter (later)
            -> CLI adapter where useful
                 -> generated framework-neutral client
                      -> React OR Svelte frontend (later)
```

The canonical contract is an **application boundary**, not an MCP boundary and not a UI model.

MCP tool definitions, HTTP route shapes, generated TypeScript types, React state, and Svelte stores are consumers/projections of the application contract. They must not independently define learner-state or adaptive semantics.

Preserve the exact current 13-tool MCP semantic boundary unless a separate reviewed durable contract/version change explicitly alters it.

## Authority boundary

Only backend domain/application rules may decide or validate, as applicable:

- evidence admissibility and provenance;
- attempt/assessment semantics;
- checkpoint advancement/current pointer rules;
- capability promotion/demotion;
- prerequisite eligibility;
- assistance ceilings/fading constraints;
- retention scheduling/completion;
- representation semantic validity;
- adaptive component promotion/authority;
- hidden transfer/retention/engineering-holdout access.

A frontend is a request/interaction surface only. Directly crafted HTTP requests must receive the same semantic acceptance/rejection as requests originating from the UI.

## Methodology before implementation

### M1 — contract SDD / source-of-truth decision

Before moving runtime code, write/review a small contract SDD/ADR that answers:

- what artifact is the **single canonical source** for application DTO definitions;
- how JSON Schema/OpenAPI are generated/projected from it;
- how TypeScript client/types are generated from the canonical artifacts;
- which metadata are contract-wide vs use-case-specific;
- how application contract version differs from DB schema version, MCP contract version, curriculum version, adaptive-policy version, etc.;
- compatibility/deprecation policy;
- deterministic serialization requirements;
- stable error/result vocabulary;
- idempotency/retry semantics at the application boundary;
- whether unknown/additive fields are tolerated and under what version rules.

Do **not** dual-author equivalent Python + JSON Schema + TypeScript contracts by hand. There must be one authority and generated/validated projections.

### M2 — behavior inventory

Inventory the existing semantic operations and classify each as command/query/use case. Record for each:

- request fields and validation boundary;
- externally meaningful result fields;
- stable error categories/codes;
- idempotency expectations;
- persistence effects;
- evidence requirements;
- observable state transition;
- current MCP mapping;
- sensitive/private fields that must never be emitted to frontend clients.

This inventory must explicitly explain how the existing 13 MCP tools map to application use cases without requiring one application use case per public tool.

### M3 — compatibility model

Define contract evolution rules before version `1.x`-style stability claims:

- additive compatible changes by default;
- breaking field/meaning changes require an explicit major contract change;
- no silent semantic reuse of an existing field name;
- old persisted/runtime records remain readable according to their owning schema/version policy;
- generated client freshness is mechanically checked;
- compatibility fixtures cover previous supported contract versions;
- deprecations require a removal/version plan rather than ad-hoc deletion.

## Planned contract surface

At minimum, E11a should be capable of expressing:

- transport-independent request DTOs;
- transport-independent success/result DTOs;
- stable error envelope with machine-readable code/category and safe public detail;
- runtime/application contract version metadata;
- identifiers/provenance references needed by clients;
- idempotency metadata for durable commands;
- deterministic serialization rules;
- explicit optionality/nullability rules.

Do not add pagination, subscriptions/WebSockets/SSE, bulk APIs, or generic query languages until a real use case requires them. If live UI updates become necessary later, define a separate versioned event/subscription contract instead of leaking persistence events directly to the browser.

## Verification plan

### V0 — architecture/static gates

Required on every E11a change:

- existing Ruff/Pyright/repository/version/architecture gates remain green;
- exact 13-tool MCP semantic boundary remains green;
- forbidden-import tests ensure transport/frontend packages cannot reach persistence internals or adaptive/curriculum semantic implementation directly;
- no generated artifact is accepted when stale relative to its canonical source;
- no secrets/deployment/local Cloudflare/WSL credentials enter generated specs, fixtures, logs, or examples.

### V1 — schema/serialization contract tests

For each canonical DTO/result/error type:

- valid examples serialize deterministically;
- serialized output validates against generated schema;
- invalid enum/type/range/nullability/required-field cases fail closed;
- stable errors contain only permitted public detail;
- field names and error codes have regression fixtures;
- round-trip tests are used where lossless round-trip is a declared contract property;
- schema generation is reproducible from a clean checkout.

### V2 — compatibility tests

Maintain fixtures for every supported published application-contract version and assert:

- current server can decode/handle supported prior requests where promised;
- current generated clients do not silently depend on fields not guaranteed by their declared version;
- additive current responses remain acceptable to older supported decoders when the compatibility policy promises that behavior;
- deliberate breaking fixtures are rejected unless the caller selects the corresponding major version/migration path.

Use explicit positive and negative compatibility matrices; do not infer compatibility from successful compilation alone.

### V3 — MCP adapter conformance

For every public MCP tool:

- MCP input is mapped into a canonical application request rather than implementing semantic rules in the adapter;
- canonical result/error is mapped back to the existing MCP contract without semantic drift;
- malformed transport payloads fail at the appropriate boundary;
- exact retries/conflicting idempotency keys preserve existing semantics;
- a transport adapter cannot bypass backend evidence/checkpoint/eligibility gates.

Use differential fixtures comparing direct application-use-case execution with MCP-adapter execution over equivalent inputs and externally meaningful outcomes.

### V4 — HTTP adapter conformance (later, before UI)

When HTTP is implemented:

- generated OpenAPI/schema matches the canonical contract projection;
- HTTP and MCP executions of overlapping use cases are differentially equivalent at the application-semantic level;
- status codes are transport concerns mapped from stable application error codes, not the source of application semantics;
- authn/authz is enforced before protected operations and cannot be bypassed by client-side state;
- request size/timeouts/retries/duplicate delivery are tested;
- malformed/extra/hostile payloads fail closed;
- no generic SQL/shell/filesystem/code-exec surface is introduced.

### V5 — generated TypeScript client assurance

Before any React/Svelte UI:

- TypeScript types/client are generated deterministically from canonical artifacts;
- clean generation produces zero uncommitted diff (or equivalent artifact-hash equality if generated code is not committed);
- strict TypeScript compilation passes;
- representative success/error/version fixtures compile and execute through the client;
- client cannot synthesize backend-only/private fields;
- generated client version declares the application contract version it targets;
- client regeneration on contract change is enforced in CI.

### V6 — frontend component/integration tests (when frontend exists)

Use framework-appropriate unit/component testing for:

- loading/success/empty/error/conflict/offline/retry states;
- form/input validation that improves UX but does not replace backend validation;
- stale checkpoint/current-version conflict rendering;
- idempotent retry behavior after uncertain network result;
- accessibility semantics, focus restoration, keyboard operation, labels and error association;
- learner-visible provenance/status fields where the product requires them.

Mocks/fixtures should be generated or schema-validated canonical-contract fixtures, not free-form hand-maintained objects.

### V7 — real disposable-backend integration

Run the client/frontend against a disposable Study OS runtime/database/evidence root. Cover at least:

`start -> attempt -> assessment -> checkpoint -> refresh/restart -> resume -> retention schedule/completion`

Also cover failure paths:

- stale pointer/version conflict;
- evidence/provenance rejection;
- invalid retention-probe closure;
- duplicate durable command/retry;
- service restart during a user workflow;
- backend unavailable/timeout and safe retry/recovery.

The browser must never be the source of truth for whether a durable write actually happened.

### V8 — browser E2E

Use Playwright or an equivalently capable browser E2E harness when a UI exists.

Minimum critical-path scenarios:

- fresh learner/session start;
- record/display attempt and assessment outcome;
- checkpoint then hard page refresh;
- backend/service restart then resume continuity;
- retention due/completion flow;
- failed/conflicting write produces a recoverable user-visible state without duplicate durable effects;
- deep-link/reload cannot manufacture privileged state.

Run a cost-bounded core suite per PR and broader browser matrix on main/nightly/release as appropriate.

### V9 — authority-negative / adversarial browser tests

Mandatory before any frontend is considered trusted as an operator surface. Deliberately bypass UI controls and send crafted requests attempting to:

- promote unsupported mastery/capability;
- cite another subject's evidence;
- advance checkpoints with stale current pointers;
- exceed assistance ceilings;
- close the wrong retention probe;
- reference hidden/protected answers;
- grant an adaptive component authority;
- submit unsupported enum/version/identity values;
- replay a prior idempotency key with changed payload.

Every case must be rejected by backend semantic/application gates. Hiding/disabling a UI button is never sufficient enforcement evidence.

### V10 — accessibility/responsive/cross-browser

Before product-facing release of a study flow:

- automated accessibility scan for critical pages/components;
- keyboard-only completion of core flow;
- focus/announcement checks for asynchronous error/success transitions;
- phone viewport + desktop viewport smoke;
- Chromium plus at least one additional independent browser engine on critical paths;
- manual spot check for issues automated accessibility tools cannot establish.

Accessibility failures affecting the learner's ability to complete a core task are release blockers, not cosmetic backlog items.

### V11 — visual regression

Visual snapshots may protect stable high-value states, but are **supplemental only**. They must not be used as evidence that learner state, semantic transitions, accessibility, or authority rules are correct.

### V12 — performance/reliability budgets

Before broad UI use, define measured budgets rather than vague claims. At minimum instrument/measure where relevant:

- application/HTTP response latency for interactive operations;
- frontend loading/render interaction latency;
- duplicate-write rate under retries (must remain zero for idempotent durable commands);
- SQLite busy/error behavior under the expected single-user concurrency profile;
- recovery after service restart/network interruption.

Set numeric thresholds only from an observed baseline and documented product need; do not invent vanity budgets before measurement.

### V13 — mutation / verify-the-verifier

When E5 infrastructure exists, include targeted mutants/negative controls for contract/adapters such as:

- bypass canonical validation;
- drop idempotency fingerprint check;
- translate a stable semantic error to success;
- allow stale checkpoint pointer;
- omit evidence scope check;
- expose a private/internal field in a generated/client response;
- adapter directly mutates persistence instead of invoking application use case.

A critical surviving mutant is a gate failure regardless of aggregate mutation score.

### V14 — security/privacy methodology

Before HTTP/UI exposure:

- explicit authn/authz threat model for local/private single-user deployment and any later remote deployment;
- least-privilege endpoint/tool permissions;
- CSRF/origin/session/cookie/token handling appropriate to the selected transport architecture;
- no secrets in OpenAPI, generated clients, browser bundles, logs or test fixtures;
- protected/private evidence content is minimized in frontend payloads;
- untrusted learner/content strings are treated as data, not executable instructions/markup;
- dependency/security scanning for frontend toolchain;
- no local-only Cloudflare/WSL/GPT Action credential or deployment-file changes as part of E11a.

Security controls must be validated at the backend/transport boundary; frontend concealment is not authorization.

### V15 — observability/debuggability

For real backend/browser integration, preserve safe correlation identifiers so a failing UI request can be traced to its application operation and durable result without exposing private evidence/secrets. Define what is safe to log before enabling broad client telemetry.

## Test-oracle hierarchy

No single frontend test is sufficient.

Use the strongest cheapest oracle for each failure class:

- semantic correctness: E4 independent reference model + domain/application tests;
- broad state sequences: Hypothesis state machine/property tests;
- contract shape/version: schema + compatibility fixtures;
- adapter equivalence: differential conformance tests;
- UI logic: component/integration tests;
- actual user wiring: browser E2E;
- bypass/authority: crafted-request negative tests;
- accessibility: automated + keyboard/manual checks;
- visual layout: visual regression only;
- verifier quality: mutation/negative controls;
- reliability/failure behavior: restart/network/duplicate/fault injection.

An LLM/model grader is never the sole oracle for deterministic contract/UI correctness. It may later supplement qualitative pedagogical/UI evaluation under a separately defined rubric.

### E11a-1 — canonical contract core

### E11a-2 — MCP conformance migration

### E11a-3 — complete canonical application boundary

### E11b — HTTP adapter (later)

Add the smallest authenticated/private HTTP surface needed by a product use case. No frontend yet required for first adapter conformance.

### E11c — generated TypeScript client (later)

Generate framework-neutral TS client/types and validate against disposable backend.

### E11d — one frontend vertical slice (later)

Choose **React or Svelte**, not both initially. Implement one narrow end-to-end study flow and pass V6-V15 applicable gates before broadening UI scope.

## Study-OS-specific frontend methodology: measurement validity and pedagogical integrity

Generic contract/browser correctness is necessary but not sufficient. A future UI changes the learner's observable environment and can therefore corrupt the measurement/control loop even when the API is technically correct.

### MV1 — frontend telemetry is evidence, not truth

Client interaction telemetry (clicks, focus, dwell, scroll, keystrokes, visibility, retries, client timestamps) is `observed` evidence with explicit provenance/version. It must not directly promote mastery, capability, representation effectiveness, retention, or adaptive authority. Derived interpretations remain separate from observed events.

Server-side durable ordering/receipt remains canonical. Client timestamps may support latency/active-time analysis but cannot silently become authoritative ordering when clocks drift, pages sleep, devices suspend, or requests are queued offline.

### MV2 — comparable timing methodology

Before #10 marks active-time/latency instrumentation complete, define timing semantics across web/mobile/desktop:

- distinguish wall-clock latency, active-visible time, input-production time, backend round-trip, and offline/hidden-tab time;
- use monotonic client measurement where appropriate and retain server receipt timestamps;
- explicitly handle background-tab/mobile suspend and reconnect;
- version the timing algorithm;
- test synthetic suspend/resume/clock-skew cases;
- do not compare raw dwell times across surfaces unless the measurement definition is comparable.

### MV3 — task-mode and assistance fidelity

The UI must preserve canonical task mode, operation, representation version, assistance ceiling and exposure metadata. A frontend convenience must not silently turn a production task into recognition, expose choices/hints, auto-complete code, show solution-bearing validation, or otherwise lower the assistance level while recording the original task label.

Tests must verify rendered affordances against the canonical item/task contract and record any assistance actually exposed before the learner answer.

Accessibility accommodations must not automatically be treated as pedagogical assistance or learner weakness. Any accommodation-vs-scaffold distinction must be explicit in the telemetry contract.

### MV4 — representation semantic fidelity

Every rendered representation used for learning/assessment must retain stable representation family/version/operation identity. Validate that transformations such as responsive layout, syntax highlighting, animation, diagrams, code editors, screen-reader text, and mobile condensation preserve the intended semantic content and do not reveal protected answer structure.

For deterministic representations, add fixture/conformance checks between canonical representation data and rendered client state. Visual snapshots alone are not semantic-fidelity proof.

### MV5 — hidden-answer/client-bundle boundary

Hidden transfer/retention answers, grader keys, protected engineering-holdout cases, future expected responses, and server-only scoring logic must never be shipped in browser bundles, source maps, static JSON, generated clients, preload payloads, or inspectable frontend fixtures.

Add build/artifact scans and explicit negative tests. The browser receives only what is required to present the current task and safe feedback.

### MV6 — offline/cache semantics

Browser/local storage is a cache/work queue, never canonical learner state. The UI must distinguish `pending`, `acknowledged`, `conflicted`, and `failed/unknown` durable writes. It must not display a checkpoint/capability/probe as committed until backend acknowledgement establishes it.

Reconnect tests should cover duplicate submission, changed-payload idempotency conflict, stale checkpoint pointer, and server state advancing on another client/session.

### MV7 — cross-surface measurement invariance

Before treating phone, desktop, GPT/MCP, and future web-app observations as comparable evidence, run matched fixture/trajectory tests showing that equivalent application operations preserve semantic metadata and outcome classification. Where the interaction mode genuinely changes the construct being measured (e.g. blank implementation vs mobile multiple choice), record it as a different task/interaction mode rather than normalizing it away.

Do not claim measurement invariance merely because all clients call the same backend endpoint.

### MV8 — UI/representation experiment methodology

Any A/B or within-person comparison of frontend representations/interaction designs is an intervention, not ordinary UI optimization. Version the variant and exposure; predefine the behavioral outcome window; separate self-report/engagement from mastery evidence; require faded/transfer/delayed outcomes for durable effectiveness claims; control prior exposure/order where practical; and retain enough provenance to reconstruct which UI/representation version the learner actually saw.

Engagement, clicks, completion rate, or time-on-page cannot by themselves justify learner-state or pedagogical promotion.

### MV9 — instrumentation integrity tests

When frontend instrumentation exists, add tests that deliberately:

- drop/reorder/duplicate client telemetry;
- background/suspend the page;
- change viewport/device during a task;
- reconnect after backend completion;
- render a stale cached task after curriculum/version change;
- expose a hint before answer and verify assistance metadata changes;
- attempt to omit exposure metadata while sending the answer;
- modify client-side score/status fields;
- submit telemetry for another subject/session.

Backend semantic state must remain valid even when client telemetry is missing or hostile. Missing optional telemetry may reduce measurement confidence; it must not be fabricated.

### MV10 — promotion evidence

Before a frontend-generated signal is allowed to influence #10 G5+ advisory/canary decisions, require explicit evidence that its capture semantics are stable, versioned, privacy-safe, and comparable enough for that decision. Software E2E success proves wiring, not psychometric or pedagogical validity.

This section is part of the #26 release methodology and should be reflected in the later E11d acceptance criteria when the first real frontend vertical slice is opened.
