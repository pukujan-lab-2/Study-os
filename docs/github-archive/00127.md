## What changed

### A1-A6 (earlier on this branch)
Player feedback keeps the answered probe visible, queues retry/check variants until feedback is acknowledged, and preserves retry/check context through repeated partial answers. The service reloads row state after acquiring its database lock and rejects attempt/confused actions outside an open probe.

A6 adds a minimal deterministic scripted learner/tutor harness over the live `/api/player/sessions` route: it compares the observed sliding-window player prefix with the pinned golden oracle, runs stub tutor roleplay by default with opt-in InferHub, and writes synthetic scorecards/transcripts outside learner evidence.

### A7 - chat-triggered current-step presentation re-render
A tutor reply may now carry a validated `regenerate_presentation` proposal (`study-os.player-presentation.v1`). The server applies it **in place** on the current step under the session row lock before responding, assigning the version server-side (`previous_version` -> `version`, monotonic per session). Step/concept identity, phase, variant, scaffold and progress are preserved; only the displayed teach text/frames change.

- `player/presentation.py` (new) owns `context`/`effective`/`validate_proposal`/`apply`/`current`. `effective()` is the single source of truth for displayed teach content and is used by both `engine.view` and tutor grounding, so the tutor cannot drift from what the learner sees after a re-render.
- Proposals that leak a probe answer, claim mastery, exceed the word budget, use code fences, or name frames outside the step are refused. If the prose is usable but the re-render is not, the generated reply is still served and the defect is reported in `validation_codes` instead of degrading to a fallback hint.
- Tutor prompt is now `tutor.v3` (packaged via `pyproject.toml` `package-data`).
- Frontend: `web/src/player/presentation.ts` applies a versioned update in place (identity match + `version > view.presentation_version` guard) without advancing the step; `CompanionPanel` uses it.
- Harness detector now distinguishes `MISSING_REGENERATE_PRESENTATION` (absent/null), `INVALID_REGENERATE_PRESENTATION` (not a v1 update, identity mismatch, version not exactly `before + 1`), `RENDER_NOT_APPLIED` (served view did not adopt it) and `RENDER_MOVED_STEP` (step/phase/variant moved). The harness re-reads the served view after the tutor turn.
- Multi-seed harness runs give each roleplay its own synthetic client IP, so per-IP signup/request budgets no longer surface as a spurious `rate_limited`.

### A8-exec - learner 1-5 step review with explicit Submit (D019 / SOS-0016)

The learner player now offers one optional per-step review: choose 1-5, type why, press Submit.

- Additive migration `0003_step_review.sql`: `ux.feedback` gains `presentation_version` and `idempotency_key`, a unique `(subject_id, idempotency_key)` scope for non-null keys, and the `ux.feedback` append-only trigger. Historical `like`/`dislike` rows keep null key/version and are neither mapped nor reinterpreted.
- `POST /api/feedback` with `target_kind: "step"` requires an integer 1-5 rating (bool/float/numeric string/0/6 rejected), a nonblank typed why, the served `presentation_version`, and an idempotency key. The server loads the session under its row lock and binds the current step/variant/version; unknown, stale, or foreign targets are rejected with zero writes.
- Exact replay of the same key returns the original `feedback_id` with one row; a changed payload under an existing key is a conflict; a fresh key deliberately appends. Concurrent identical submits collapse to one logical row at the database layer (`ON CONFLICT ... DO NOTHING RETURNING`).
- A review never advances the step, phase, variant, or progress, and never writes a `learn.*` review event. Numeric opinion and rationale are `self_reported` UX feedback.
- `FeedbackBar` renders five labeled choices, a labeled typed why, and an explicit Submit. Choosing or typing makes no request; Submit is disabled until both are valid. A same-step re-render keeps the draft and its idempotency key and updates the presentation version it is about; a step/variant change clears it. A failed request keeps the draft and key for retry.
- Admin read model separates ordinal 1-5 step reviews from historical thumbs and does not fold one into the other.
- Tutor-message feedback and decomposer review are unchanged.

### A10-exec - live tutor re-render product fix (SOS-0018 gate now green)

The A9b-exec live gate failed with `MISSING_REGENERATE_PRESENTATION` x21: the live InferHub tutor answered same-concept clarification turns with a text-only reply (`regenerate_presentation: null`, "I can't re-render during this question"). This slice fixes the product, not the harness. Commit `9b2b1ab`.

**Diagnosis (live, reproduced against both routes)**
- `TOOL.regenerate_presentation` was typed `["object", "null"]` and the prompt only described the case where the learner explicitly asks for a new render, so the primary route answered `null` on redirect/clarification turns.
- The fallback route (`cb/deepseek-v4.1-flash`) spent 430 of a 550-token cap on hidden reasoning and returned truncated tool arguments; the transport reported that as `no_tool_call` and then treated both routes as failed (`model_unavailable:all_routes_failed:no_tool_call,no_tool_call` x8 in the A9b advisory).
- One dropped or truncated tool call ended the turn with no retry.

**Product changes (all under `src/`)**
- `presentation.regeneration_allowed()` is now the single source of truth for the refusals `validate_proposal()` enforces, and the tutor turn context carries it, so the model is told whether this turn may refresh the card (including redirects and answer-seeking turns) instead of guessing. `validate_proposal()` delegates to the same function.
- `tutor.v3` prompt + golden rules state that contract explicitly; the tool property is a concrete object (optional, so it can simply be omitted rather than answered `null`).
- One retry per model call, with a generous completion cap for reasoning routes.
- A reply that still drops the refresh gets one focused render-only call with a dedicated `regenerate_presentation` tool; a still-missing refresh is recorded in `validation_codes` (`RENDER_UNAVAILABLE` / `render_unavailable:*`) rather than passing as generated content, and an identical authored card is never re-published as a new version. Step/concept identity, phase, variant, version monotonicity and the no-answer-reveal rule are unchanged.
- A card refresh clears the adapt suggestion for that turn (both rewrite the displayed card); `suggested_action` only accepts a real adapt kind, so a literal `"null"` string no longer reaches the client.
- `InferHubLLM` distinguishes truncated tool arguments (`invalid_tool_arguments`) from a missing tool call (`no_tool_call`) in its recorded attempts.
- No `web/src/` change was needed: `applyPresentation` already adopts a versioned update for the same step/concept.
