# Issue #52: [P3] Operational learning, durable evidence, and structured curriculum

- State: closed (2026-09-24)
- Opened by Pukujan on 2026-09-03
- Original: https://github.com/Pukujan-lab/Study-os/issues/52

## Purpose

Make real Study OS usage the primary product-development loop while protecting the durable assets that matter: learner evidence, architecture, data semantics, curriculum provenance, and representation/intervention history.

This tracker resets execution priority without erasing historical issue lineage.

## Product direction

Current learner-facing surface: **GPT app**.

Current product loop:

```text
structured source material
 -> learner attempt
 -> observed/self-reported friction
 -> diagnosis hypothesis
 -> representation / information / assistance / granularity operation
 -> learner response
 -> fade / restore source difficulty
 -> transfer / retention when warranted
 -> learner + system evidence
```

A dedicated frontend and richer multimodal surfaces remain valuable later, but are not the current critical path.

## P3.0 — Durable-or-recoverable evidence (highest priority)

Reported HTTP 502 failures during real learning mean the GPT -> local Study OS path is not dependable enough.

### Invariant

> No silent learner-evidence loss.

A learning interaction must be either durably acknowledged locally or explicitly known to be missing/uncertain and recoverable through reconciliation/backfill.

## P3.3 — Representation and operational adaptive learning

Current candidate operation/failure families come from real use and research. They remain versioned hypotheses until semantics/evidence stabilize.

### Operation candidates

- representation translation;
- identifier/variable-name normalization;
- language simplification;
- information compression/expansion;
- progressive disclosure;
- task decomposition/recomposition;
- concrete example / deterministic trace;
- pseudocode/code translation;
- hinting;
- assistance fade;
- source/original representation restoration.

### Failure candidates

- representation translation overhead;
- variable-name semantic interference;
- information overload / under-information;
- over-help / under-help;
- over-decomposition / under-decomposition;
- answer leakage;
- transformation-fidelity failure;
- dependence on normalized representation.

- [ ] extend operational schemas only when real episodes require stable new semantics;
- [ ] keep learner score/evidence separate from system/intervention score/evidence;
- [ ] evaluate immediate effect separately from fade/transfer/retention;
- [ ] preserve transformation provenance from source representation to adapted representation and back.

## Engineering stance

Keep architecture and data protections:

- PDD/SDD/invariants;
- migrations/contracts;
- provenance/privacy;
- idempotency/recovery;
- architecture ownership boundaries;
- compatibility where persistent semantics require it.

Implementation code is replaceable. Broader hardening methods are risk-driven rather than blanket near-term gates.
