## Purpose

Contains Duplicate also established that structural/schema/progression validity is insufficient: learner-visible semantics can still be wrong. The generic 14-problem run then proved the model/schema path can generalize operationally, while exposing the need for completion-driven acceptance.

## Architecture

```text
raw problem
    ↓
Luna strong-inference decomposer skill
    ↓
ALGORITHM GRAPH
objects → state → invariant → transition/recurrence → termination → solution
    ↓
BACKWARD PREREQUISITE EXPANSION
    ↓
LEARNING GRAPH
primitive meaning → vocabulary/symbol grounding → relation → bridge → control flow/recursion → integration
    ↓
TeachingPlan candidate
    ↓
checklist + schema + deterministic semantic validation
    ↓
actual learner message
    ↓
Luna diagnosis + evidence-bound learner outcome
    ↓
deterministic controller authorizes one operation
    ↓
Luna learner-visible generation
    ↓
semantic / vocabulary / representation validation
    ↓
learner
    ↺ until actual completion
```

Turn count is a metric only. The configurable `250 exchanges/problem` value is an anti-loop ceiling, not an expected lesson length or success condition.

## Representation and vocabulary

The calibrated learner benefits from grounded compact symbolic/algebraic/state-transition reasoning when it simplifies the problem. Do not turn that into a universal equation-first policy.

Preferred pattern:

```text
ground object / simple vocabulary
→ ground symbol or technical term
→ one relation/action
→ changed example
→ generalize
→ derive repeated transition / recursion
→ derive control flow
→ derive code
```

Vocabulary policy prioritizes semantic accuracy, then comprehension, then brevity. Ground a simple expression before introducing a technical term where helpful (`node with no children` → `leaf`, `line of nodes waiting their turn` → `queue`). Reject undefined terms, synonym drift, term overload, premature formalism, symbol-before-meaning, and metaphors that change an invariant.

The learner may be wrong, partial, uncertain, request elaboration, or need a representation change. The learner must **not** be required to discover and repair tutor semantic/dependency/representation failures.

## Rotating development evaluation

Routine engineering iterations use **4 public completion-driven problems** selected automatically after candidate freeze:

- deterministic recorded seed;
- no overlap with the immediately previous rotating batch;
- without-replacement coverage across an epoch;
- maximize structural-family diversity when possible;
- persist the selected batch before inference.

The public 14-problem corpus is regression/calibration data. Four rotating public problems are **not** a hidden holdout.

## Hidden promotion boundary

Unburned hidden holdouts are owned by a separate local evaluator process/agent, not the engineering/prompt-fixing Luna.

Recommended boundary:

```text
engineering Luna
  writable repo
  no STUDY_OS_HOLDOUT_DIR
      ↓ frozen candidate
holdout evaluator
  read-only candidate
  private STUDY_OS_HOLDOUT_DIR
      ↓ inject problem statement only
measured decomposer / teacher / student
  no holdout filesystem path
  no evaluator oracle
      ↓
holdout evaluator oracle check
      ↓
sanitary verdict / failure categories only
```

If raw hidden case detail is needed to make a fix, the case is **burned**: remove it from hidden eligibility, move a reviewed version into public regression, fix against it publicly, and replenish the hidden bank.

## Prompt / schema / deterministic authority

- **Skill + prompt** steer decomposition/diagnosis/representation/vocabulary/generation.
- **Schema** externalizes algorithm graph, learning graph, terms, symbols, semantic roles, evidence, completion conditions, and provenance.
- **Deterministic code** owns legal transitions, evidence binding, semantic/vocabulary/representation invariants, retry/verification policy, completion, anti-loop behavior, assistance boundaries, and provenance. It does not author lesson prose.
- **Acceptance/calibration** judges learner-visible completion and quality without leaking hidden evaluator answers to the teacher.

`src/study_os/prompt_registry.py` already provides immutable content-addressed prompt versions/hashes. Material prompt changes must register new versions rather than overwrite historical prompt semantics.

### Critical acceptance bug
`tools/check_model_tutoring_all_dsa.py` validates that each recorded turn is internally consistent with the generated plan/controller, but it never requires a scenario to actually progress through the plan or reach its terminal/final concept.

The committed Sliding Window run demonstrates the hole. Cause: the diagnosis policy systematically treats semantically correct confirmation-seeking replies such as `At position 4 with k = 2, the window is 6 and 1, right?` as `not_yet` solely because they are phrased as questions. That is too conservative for progression evidence in this test and creates a deadlock.

### Required generic fix
1. Strengthen the all-DSA acceptance gate to require meaningful plan coverage/progression per scenario. At minimum, final state must reach the plan's final concept; preferably record concepts visited and completion-evidence coverage.
2. Add a negative-control test where all 15 turns remain on concept 0 and assert the gate fails.
3. Version the diagnosis prompt (do not overwrite v1) so a semantically correct proposition can count as `demonstrated` even when expressed as a confirmation question; uncertainty/hedging should be judged from content, not punctuation alone. This still must require verbatim evidence and must not imply mastery.
4. Rerun the full 14×15 learner-visible experiment after the prompt/controller/gate change.
5. Manually review the new transcripts, especially Sliding Window and other low-calibration scenarios.

### Prompt-evaluation gap
The committed prompt evaluation is structural only for metamorphic variants: `live_model_variants_executed=false`. Its `status=passed` therefore does **not** prove the candidate prompts were evaluated on live paraphrase/value variants. Add actual live held-out/model variants before treating prompt evaluation as complete.

This defeats the intended rotating-development anti-overfit property. Preserve qualification reset for a new candidate, but do not reset the *development rotation history* used to choose the next diagnostic batch.

### 2. Generated TeachingPlans are still the old coarse v0.1 shape

The preserved plans use `study-os.teaching-plan.v0.1` and `study-os.model-tutoring-decompose.v1`. The inspected plans contain only 4–5 macro concepts. Reliability of the new reverse-solution decomposition therefore has not actually been demonstrated yet.

### 3. Concrete semantic evidence false positive in Number of Islands

Plan concept `explore-component-with-stack` requires `component-exploration-evidence`: the learner should describe marking a discovered cell, pushing it, and exploring valid four-direction neighbors until the stack is empty; the concept also owns the component-completeness invariant.

But turn 8 advances from `explore-component-with-stack` to `return-total-component-count` on only:

> `I should mark every newly discovered cell as 0 before pushing it onto the stack.`

That proves mark-before-push, not full component exploration/completeness. The teacher itself supplies `Continue popping cells ... when stack is empty`, then the controller advances. This is exactly the class of evidence over-credit we wanted to remove.

Required generic fix: advancement evidence must entail *all required evidence/invariants for the active node*, not merely one sub-operation contained inside that node. This also argues for finer-grained decomposition: `mark-before-push`, `pop/inspect-neighbors`, `discover-valid-neighbor`, and `frontier-empty => component-complete` should be distinct dependencies if independent evidence is expected.

### 4. Artifact/ledger state is not a clean qualification pass

The current top-level qualification ledger at this head is `RUNNING`, epoch 2, with no completed public batches and no hidden batches. The preserved pre-bound-fix ledger is also `RUNNING`; epoch 10 records the public batch as `passed: false` / `runner_exit: 1`.

The preserved 75-row merge is valuable evidence, but it is not a clean atomic qualification-run receipt. Fix lane-completion/merge finalization so a batch can be trusted without manual preservation/reconstruction.

### 5. No hidden promotion evidence yet

Both ledgers have `hidden_scenario_ids: []` / no hidden batches. That is fine for development, but it means this cannot yet satisfy `DECOMPOSITION_RELIABILITY_QUALIFIED`.
